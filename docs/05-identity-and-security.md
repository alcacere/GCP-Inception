# 05 · Identity and Security

In the original project, security came mostly from **what wasn't exposed**: one port,
a private network, secrets as files. On a public cloud the biggest attack surface is
**identity**: who (or what) is allowed to call which API. This page covers that layer.

---

## IAM: principals, roles, policies

**What it is.** An IAM **policy** binds **principals** (users, groups, service
accounts, federated identities) to **roles** (collections of permissions) on a
**resource** (organization, folder, project, or an individual resource such as one
secret or one bucket). Policies are inherited down the hierarchy.

| Role type | Example | Use |
|---|---|---|
| Basic | `roles/owner`, `roles/editor` | Too broad. Avoided except for my own bootstrap user |
| Predefined | `roles/run.invoker`, `roles/cloudsql.client` | The default choice |
| Custom | `projects/…/roles/inceptionDeployer` | Only if no predefined role is narrow enough |

**Rule used everywhere in this project:** grant the narrowest predefined role, on the
narrowest resource possible (a single secret, not the project).

**References**
- IAM overview: <https://cloud.google.com/iam/docs/overview>
- Roles reference: <https://cloud.google.com/iam/docs/understanding-roles>
- Use IAM securely: <https://cloud.google.com/iam/docs/using-iam-securely>

## Service accounts: one per workload

**What it is.** A service account is an identity for software. A workload *attached*
to a service account (a VM, a Cloud Run service) gets short-lived tokens from the
metadata server automatically, so **no key file is needed**.

**How this project will implement it**

| Service account | Used by | Roles (scope) |
|---|---|---|
| `sa-wordpress` | Cloud Run `wordpress` | `cloudsql.client` (project), `secretmanager.secretAccessor` (on each of its secrets only), `storage.objectUser` (uploads bucket only), `logging.logWriter`, `monitoring.metricWriter` |
| `sa-grafana` | Cloud Run `grafana` (and the Phase 1 Grafana container, through `sa-host`) | `monitoring.viewer`, `logging.viewer` (project). Read-only: it can't change anything it displays |
| `sa-host` | Phase 1 VM | `secretmanager.secretAccessor` (its secrets), `logging.logWriter`, `monitoring.metricWriter`, `monitoring.viewer` (for Grafana) |
| `sa-deployer` | Terraform in CI | Admin roles for the managed products, `iam.serviceAccountUser` on the workload SAs only. Never `owner` |
| `sa-ci-push` | Image build job | `artifactregistry.writer` on the repository only |

Default compute service accounts (which get `Editor` automatically) are **never
used**. Each workload names its own service account explicitly.

**References**
- Service accounts overview: <https://cloud.google.com/iam/docs/service-account-overview>
- Best practices for service accounts: <https://cloud.google.com/iam/docs/best-practices-service-accounts>

## Workload Identity Federation (keyless CI)

**What it is.** GitHub Actions can issue an **OIDC token** describing the job
(repository, branch, workflow). WIF lets GCP **trust that token** and exchange it for
a short-lived GCP token that impersonates a service account. No JSON key ever exists,
so there is nothing to leak and nothing to rotate.

```
GitHub Actions job ──OIDC token──► STS (WIF provider: attribute condition
                                    assertion.repository == "<owner>/inception-gcp")
                                  ──► short-lived token for sa-deployer ──► Terraform / gcloud
```

**The important part is the attribute condition.** Without it, *any* GitHub repository
could impersonate the account. The condition pins the repository, and the deploy
workflow can additionally be pinned to `refs/heads/main`.

See [ADR 0006](adr/0006-keyless-ci-with-wif.md).

**References**
- Workload Identity Federation: <https://cloud.google.com/iam/docs/workload-identity-federation>
- With deployment pipelines: <https://cloud.google.com/iam/docs/workload-identity-federation-with-deployment-pipelines>
- `google-github-actions/auth`: <https://github.com/google-github-actions/auth>

## Secret Manager

**What it is.** A managed store for small secrets. Each **secret** holds
**versions**. Access is controlled per secret with IAM and every access is recorded in
audit logs. Replication policy and optional customer-managed keys (CMEK) are set per
secret.

**Mapping from the original project**

| Original | GCP |
|---|---|
| `secrets/db_password.txt` generated by `generate-secrets.sh` | Secret `db-password`, version added once by `tools/seed-secrets.sh` |
| `secrets:` in compose → `/run/secrets/db_password` | Phase 1: the startup script writes it to a tmpfs. Phase 2: Cloud Run **secret volume mount** at the same kind of path |
| Rotation = edit the file + restart | Add a new version → Cloud Run uses `latest` or a pinned version → new revision |

**Keeping secret values out of Terraform.** Terraform creates the secret *resource*
and its IAM bindings, but **not the version** (the value). Values are added by a
small script that generates them locally and pipes them straight to
`gcloud secrets versions add --data-file=-`, so they never touch disk or Terraform state.

Cloud SQL users are the one exception worth knowing about: the password must be set
on the instance too. The plan is to use **Cloud SQL IAM database authentication**
where the client supports it, and otherwise to set the password from the secret in
the seeding script, not in Terraform.

**References**
- Secret Manager overview: <https://cloud.google.com/secret-manager/docs/overview>
- Best practices: <https://cloud.google.com/secret-manager/docs/best-practices>
- Cloud Run secrets: <https://cloud.google.com/run/docs/configuring/services/secrets>

## Identity-Aware Proxy (IAP)

**What it is.** IAP puts an identity check in front of an application or a TCP port.
Access depends on *who you are* (IAM role `iap.httpsResourceAccessor` or
`iap.tunnelResourceAccessor`), not on *where you connect from*. This is Google's
implementation of the zero-trust model (BeyondCorp).

**How this project will implement it**
- **Phase 1 SSH.** The VM has no firewall rule for public SSH. Only the IAP range
  `35.235.240.0/20` may reach port 22, and only my user has the tunnel role:
  `gcloud compute ssh inception-host --tunnel-through-iap`.
- **Grafana (Phase 1).** Port 3000 is never published. It is opened with
  `gcloud compute start-iap-tunnel inception-host 3000 --local-host-port=localhost:3000`.
- **Grafana (Phase 2).** The `/grafana/*` backend service has IAP on. Grafana trusts the
  signed IAP header (JWT) as the login, so there is no Grafana password to leak
  ([11](11-observability.md)).
- **Adminer (optional, Phase 2).** If kept, it sits behind the load balancer with IAP
  turned on for that backend, so only my Google identity can open it.

**References**
- IAP overview: <https://cloud.google.com/iap/docs/concepts-overview>
- TCP forwarding: <https://cloud.google.com/iap/docs/using-tcp-forwarding>

## Audit logs and other guardrails

- **Cloud Audit Logs**: Admin Activity logs are always on and free. Data Access logs
  for Secret Manager will be enabled, so every secret read is recorded.
- **Shielded VM + OS Login** on the Phase 1 host.
- **Uniform bucket-level access + public access prevention** on every bucket except
  the portfolio bucket, whose public read is intentional and documented.
- **Organization policies** (for example "no service account key creation", "no
  external IPs on VMs") are listed in the roadmap, because they need an organization.

- Cloud Audit Logs: <https://cloud.google.com/logging/docs/audit>
